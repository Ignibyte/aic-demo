# Staff

Ridgeway Motors' staff sign in to Lotline, and everything under `/app` is theirs alone. The module builds on AIC's Auth: `AIC\Auth\Application\Authenticator` signs a member in and out and keeps their id in the session, `PgcryptoPasswordHasher` hashes passwords with Postgres pgcrypto (bcrypt), and `RequireAuthenticationMiddleware` sends a signed-out visitor to anything under `/app` to `/sign-in?next=…`.

The manifest binds `UserProvider` to `StaffRepository` and `PasswordHasher` to `PgcryptoPasswordHasher`, runs the middleware after the session over the `RouteAuthConfig` that the `AccessRules` factory makes (every module's protected prefixes, sign-in at `/sign-in`), and protects `/app`. It exports `StaffPages` (the staff pages' document) and `StaffSession` (who is signed in), which `inventory`, `customers`, `sales` and `site`'s navigation use, and the pieces a record's pages share (#6, #7), so each module keeps no copy of its own:

- `StaffPanels`: a record page's one wide panel in the staff document, its id stem given by the module's factory (`vehicle`, `customer`, `sale`), and the warning page a 404 or a refused form shows in it;
- `StaffNotices`: the one line a save or a delete keeps in the session (`staff.notice`) for the page it redirects to, which takes it before anything else (a 404 for a record gone meanwhile included, so no notice waits for a later page), shows it as a success `Notice` and clears it;
- `StaffSeals` (in `Form/`): AIC's signed envelope sealing a record's path in its edit and delete forms, and the check that a post's envelope is whole and seals the path it was posted to.
- `StaffRequests`: a query parameter and a route attribute read as plain text through a native `string` return (a list, or a value that is no string, reads as empty), for `customers` and `sales`; elephc does not narrow an untyped value by `is_string()`.
- `StaffMember` and `Role` (in `Entity/`): who `StaffSession::member()` gives and their role, by which `photos` lets a sales manager or an admin change a vehicle's photos and a salesperson only see them (#16).
- For the `settings` module's staff admin (#22): `AccountRepository` (the members' reads and guarded writes), `StaffRepository` (a password hash set), `StaffAccount` (a member as the settings read them), `AccountWrite` (what a guarded write did) and `Roles` (every role in order, and a stored one read back).

## Data

`CreateUsersTable` makes `users`: an identity `id`, `email` (unique; the login), `name`, `role` and `password_hash`, with `created_at`. `StaffTable::type()` is its AIC entity type, the one place the table is named (#14, AIC #185); it is exported, so `sales` references a member through it and reads its sellers and its form's staff from it. `StaffRepository` reads and writes through AIC's `EntityStore`: `save()` upserts on the email, and `add()` inserts when the login is new and otherwise changes the password alone. `AddUserDeactivation` (#22) adds `deactivated_on`, a nullable date: AIC adds a column to a table that has rows only as nullable, so null is active, which every earlier row is. It also makes `staff_today`, the database's today as a one-row view, which a deactivation is dated by. `StaffRepository::credentials()` gives none for a deactivated member or one whose hash is empty (a member an admin added, until their password link sets one), so the Authenticator checks the decoy hash and the sign-in says "Wrong email or password.", telling nothing about the account. `AccountRepository` serves the settings: every member, one by id or login, an add with an empty hash, and two guarded writes, each one transaction. `change()` reads the active admins `FOR UPDATE` in id order, then the member, refuses a copy whose name or role is no longer the one shown (stale), and refuses to leave no active admin; taking the locks in that one order, two admins demoting each other at once serialize rather than deadlock. `activate()` does the same for a deactivation. Each answers an `AccountWrite` outcome: saved, stale, last-admin or missing. `StaffRepository`, exported since #22, keeps the two plain writes: `setPasswordHash()`, which stores the hash a settings link made, and `remove()`. Roles are `Role` cases stored as `admin`, `sales_manager` and `salesperson`; `Roles::stored()` reads a stored value back and refuses any other. `Role::label()` is written as if/return, since elephc cannot lower a `match` over enum cases yet (AIC #164).

## Pages

- `GET /sign-in` (`SignInPage`): the form from `SignInForm`, carrying `next`. The email is a text field, so a login such as the gate's `gate` passes the browser.
- `POST /sign-in` (`SignInPost`): on success a full visit (303) to `next` when it is a path on this site, else to `/app`; a wrong email or password answers the form again as 422 with "Wrong email or password.", the email kept and the password never.
- `POST /sign-out` (`SignOutPost`): ends the session, a full visit (303) to `/`.
`GET /app` is the `dashboard` module's page (#8), which greets the member in the header; the staff module keeps the prefix it protects and the sign-in's landing there. `StaffPages::page()` takes an optional last argument, the line the theme's `TopBar` writes under the title, which the dashboard's greeting uses; every other page leaves it empty.

`content` holds the panel grid alone. From #14 until #15 `StaffPages::page()` also took lead parts, set in `content` before the grid, and `StaffPages::target()` gave a lead part's path, because only a region's child carried a Tessera props token; under protocol 2 a part inside the grid carries its props and is read by its anchor, so both went.

`StaffPages::page()` titles the document with the top bar's title (#11): AIC's `PageDocuments` writes it as `{title} · Lotline` in the whole page and in every Tessera fragment, so the browser's tab follows each visit. Every staff page goes through it, directly, through `StaffPanels` or through `SignInForm`, so a list is titled `Inventory · Lotline`, a record by its heading (a vehicle's year, make, model and trim, a customer's name, `Sale of the …`) and a form or a warning by its title. A page whose heading should not be its title names one as the optional last argument, `$documentTitle`; the dashboard, whose heading greets the member, passes `Dashboard`. The inventory list, `/app/inventory`, is the `inventory` module's.

`StaffStanding` (#22), a middleware the manifest lists before the sign-in guard, holds every signed-in session to the users table on each request. It reads the member by the id AIC's Authenticator keeps. A member deleted or deactivated since they signed in is signed out there, so the guard sends them to sign-in from anything under `/app`. Anyone else has the name, email and role the table holds written into their session when they differ, so a role an admin took away is gone on the member's next page, and every role check reads the table's role. A visitor's request reads nothing. The sign-in page shows the one-time line `StaffNotices` keeps for it, such as the settings' "Your password is set. Sign in with it."

`AccountMenuBlock` puts the account corner in the `header` region on every page, after the page's `TopBar`: the theme's `SignedInMenu` (name, role, email and the sign-out form; the block sets its id stem, `account`, so its ids are `account-name`, `account-role`, `sign-out-form` and `sign-out`), or a "Sign in" link. A block takes no services, so `StaffSession` keeps the signed-in member's email, name and role in the session at sign-in, and both the block and the dashboard read them there. Signing out clears the whole session.

## Commands

- `bin/aic user:add {login} {password}`: exactly those two arguments. A new login becomes an admin named by its login; an existing one only gets the new password. gate:23 and `vendor/bin/aic-gate browser` make their own `gate` user with it.
- `bin/aic staff:seed`: no arguments. It saves the admin from `LOTLINE_ADMIN_EMAIL`, `LOTLINE_ADMIN_NAME` and `LOTLINE_ADMIN_PASSWORD` (exit 2 without them), and, when `LOTLINE_STAFF_PASSWORD` is set, four invented staff sharing that password: Dana Whitlock (sales manager), Leo Fontaine, Marcus Hale and Priya Natarajan (salespeople), all at `@ridgeway-motors.test`. Run again, it updates them. `config/staff.php` reads the settings, the one place that touches the environment, and the `StaffSettings` factory hands them over. No password lives in the repository; on a dev box DDEV's ignored `.ddev/config.local.yaml` holds them.

- `bin/aic user:remove {login}` (#22): exactly one argument. It deletes the member and their kept notifications (AIC's `Inbox::forget()`); their password links go with them by cascade. A member a sale, a hold or a lead names stays: the database refuses the delete (SQLSTATE 23503) and the command says to deactivate them in the settings instead (exit 1). No such member exits 1, and anything but one argument exits 2 with the usage. gate:23 runs it to remove its newcomer at the end of each pass.

Run `bin/aic migrate` first. From the host, point it at DDEV's published Postgres port (`PGPORT`, from `ddev describe`).

## Checks

`config/native-site.json` walks the flow: an anonymous `/app` (303), the sign-in page, a refused password (422), sign-in (303), `/app` signed in (200), sign-out (303) and `/app` again (303). The Playwright tests in `tests/browser/` look at it in a browser: a signed-out `/app` comes back after sign-in to the dashboard's greeting, the header shows the name, a refused password shows the error, and signing out locks `/app` again.
