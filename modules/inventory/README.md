# Inventory

The vehicles on Ridgeway Motors' lot, for signed-in staff: listed at `/app/inventory`, and each one's record viewed, added, edited and deleted below it (#5), with its photos (#16). The module requires `staff`, `photos` and `finance` (#26), whose payment calculator each vehicle's page shows: every page sits under its protected `/app` prefix, so a signed-out visitor goes to `/sign-in?next=…` and comes back, and every page uses its exported `StaffPages` document.

## Data

`CreateVehiclesTable` makes `vehicles`: an identity `id`, `vin` (17 characters, unique), `year`, `make`, `model`, `trim`, `body_style`, `mileage`, `exterior_colour`, `list_price` and `cost` (whole dollars, integers), `status`, `added_on` (a date), `created_at` and `updated_at`. Statuses are `VehicleStatus` cases stored as `in_stock`, `on_hold` and `sold`; `VehicleStatuses::stored()` reads a stored value back and refuses any other, and `tone()` gives each its badge colour. The seed's `SeedVehicles::status()` chooses its case through a `match` rather than a ternary: elephc types a ternary between two cases as their backing string, which the native site's build refuses (no AIC ticket carries that limit yet).

`VehicleTable::type()` is the table's AIC entity type, the one place it is named (#14, AIC #185); it is exported, so `sales` references a vehicle and reads its choices through it and the dashboard counts it. Every repository reads and writes through AIC's `EntityStore` and `EntityQuery`, never the raw database (gate:9). `VehicleRepository` reads for the list and saves for the seed: `save()` upserts on the VIN, `makes()` lists the makes on the lot (the field's distinct values), and `count()` and `page()` read what a list's query keeps, its search over make, model and VIN and its filters on one query. `VehicleRecordRepository` reads and writes one vehicle by its VIN for the record's pages: `find()`, `taken()`, `create()` (an insert that skips a taken VIN), `update()` and `delete()` (changes by query, the delete keeping a sold row) and the database's `today()`. Both read rows through `VehicleRows`, which also gives a vehicle's values by field, and the list's sort field comes from the first's own list.

`AddVehicleLocation` adds `vehicles.location` (#29), where on the lot a vehicle stands: a `VehicleLocation` case stored as `front_row`, `showroom`, `back_lot` or `service_bay`. AIC adds a column to a table that has rows only as nullable, so null means no location yet, which every vehicle stored before has; the list shows it as a dash. `VehicleRows` reads it into `Vehicle::$location` but leaves it out of the values a save writes, so the full form, a row's save and the seeds keep a vehicle's location as it is, and only a bulk move changes it. `VehicleStatuses::locations()` lists them in order and `location()` reads a stored value back.

The database's today is a view: `CreateTodayView` makes `inventory_today` (`SELECT current_date AS today`), and `TodayRepository`, exported, reads it through a read-only entity type. The entity API has no query for the date, and a view is where a module writes the SQL it needs; the vehicle form, the sale form and the dashboard's version all count from it, so the date stays the database's.

The public side reads the vehicles for sale through three exports (#17), which the `storefront` module uses. `ListedVehicleRepository` reads only rows whose status is `in_stock`, all through the view `vehicle_listings` (#33): the makes and the model years for sale, the count and a page of what a `ListingQuery` keeps (a make, a year, a price range and a sort: `newest`, by `added_on` descending, or `price` and `-price`, by `list_price`; each then by VIN), every vehicle of a make for the feed, and the one of a year with a key. It reads each row as a `ListedVehicle`: the row's id, which its photos refer to, what it is, its mileage and list price, and its key, the first 6 hex digits of the SHA-256 of its VIN, which the public slug ends with. A `ListedVehicle` has no VIN and no cost, so nothing outside this module can show them. The one exception is the XML feed for listing sites (#37), which matches cars by VIN: `feed()` reads every car for sale, in `all()`'s order, as a `FeedListing` (exported, in `src/Entity/Feed/` since `src/Entity/` is at gate:26's cap), which holds the car's `ListedVehicle` and its VIN and nothing else, so the cost, status, location and dates stay here. The key has one source, the view's `listing_key`, worked out in SQL: each read takes it from the row, and the one of a year with a key is found by both columns in SQL.

## The list

`InventoryListPage` answers `GET /app/inventory` with the panel `InventoryList` builds: the theme's `FilterBar`, then the results, keyed `table`: a `TableResults` holding the kept sort, the `DataTable` of `TableRow`s, 15 vehicles a page, and its `Pagination` past one page. The results are an AIC `SourcedComponent` (#14, AIC #192): `InventoryResults` holds the repository and the parsed query and counts, pages and reads the vehicles in `build()`, which the render pass calls only when it renders them, so a Tessera answer for anything else never reads them. `InventoryTable::results()` lays them out. Every control is a plain GET parameter, so the list works without JavaScript.

With JavaScript, a filter, a sort and a page each ask Tessera for the results alone: the filter form, each sortable head's link and each page link carry `data-target="@inventory-results"`. That is the results' anchor (AIC #188, `InventoryTable::ANCHOR`): `InventoryList` puts it on the panel's part `table`, AIC prints it as `data-t-anchor` on the results' root element, and Tessera sends the path it finds there, so no code here spells the path and a wrapper or a reorder of the page cannot strand it. The theme's `TableResults` holds them in one element, which Tessera needs (protocol 1 and 2), since a component is marked on its one root element. The answer is one fragment, the sidebar, header and filter bar stay as they are, and Tessera pushes the URL, so back and forward ask for the results again. The filter bar's "Clear" link refreshes the whole `content` region, so it clears the fields too. The sort the filter form sends is a theme `FormValue` inside the results, a hidden `sort` field tied to the form by `form="inventory-filters"`, so it changes with the table on a sort; the form holds no copy of its own, and a plain GET sends it last, as before.

| Parameter | What it does | Default |
|---|---|---|
| `q` | Searches make, model and VIN, ignoring case | none |
| `make` | One make on the lot | every make |
| `status` | `in_stock`, `on_hold` or `sold` | every status |
| `min_price`, `max_price` | List price bounds, whole dollars, 1 to 7 digits | no bound |
| `sort` | `year`, `make`, `model`, `mileage`, `price`, `status` or `added`; `-` before it reverses | `-added`, newest on the lot first |
| `page` | The page, 1 to 9999 | 1 |

`InventoryQueries` checks each parameter on its own: one that is missing, unknown or malformed falls back to its default and leaves the others alone, and a page past the last shows the first. A sortable head links to its column ascending, or to the other direction when it is the sort, with `aria-sort` on it. `InventoryLinks` writes every link with the search and filters kept and only the parameters that differ from their defaults; a sort starts again at page 1. The status cell is the table row's badge in `StatusBadge`'s tone. The list never shows the cost.

### Search as you type

The search box is the theme's `SearchField` (#27), in the filter form with the id `filter-q` and the name `q`. Each pause of 300 ms in typing submits the form (`data-on:input__debounce.300ms="el.form.requestSubmit()"`), and Tessera sends that as the same visit a Filter click makes: the results alone, by `@inventory-results`, with the query in the URL, so a reload shows the same list. There is no `@get`: an action never touches history in Tessera, so it could not keep `?q=`. The form carries `data-push="replace"` (Tessera #37), so each pause replaces the list's history entry rather than adding one; the Filter button carries `data-push="push"`, which overrides the form's, so a pressed Filter still adds an entry, and a sort or a page link adds one as before. The box sits outside the results, so their answer leaves its focus and caret alone, and `data-focus-key="inventory-search"` names it for Back and Forward. On Back and Forward the list, its count and the URL follow the entry, and the box keeps the text last typed, since no answer redraws it. While the request is out Tessera marks the form `data-loading`, which shows the box's spinner, and the results `aria-busy="true"`, which dims them. A newer search supersedes one still in flight, and a late answer is dropped (Tessera #38). With JavaScript off the form is the plain GET form with its Filter button.

The search reads through `EntityQuery::search()`: an `ILIKE '%text%'` for each of make, model and VIN, joined by `OR`, with `%` and `_` matched as typed. `whereAny()` does not apply, since a `Comparison` is `=`, `<>`, `<=` or `>=` and none matches part of a value.

The list links each VIN to its vehicle's page and offers "Add a vehicle" above the filters; after a delete it shows a notice saying which vehicle went.

### Edit in the row

A vehicle's list price and status are edited in the list itself (#28). Each row is `VehicleRowForm`'s, keyed by its VIN, anchored `vehicle-<VIN>` and carrying, as its Tessera props, the vehicle's path sealed by `StaffSeals::props()`. Its price and status cells link to the vehicle's edit page, which is what a page without script follows; with script, a click asks `@get('/app/inventory/<VIN>/row/edit')` and Tessera names the row alone. `EditRow` is the row as a small form: the price a text box, focused with its text selected, the status a select, Save and Cancel. Enter in a field submits the row's form, as Save does, and the form sends `@put('/app/inventory/<VIN>/row', {form: true})` unless it already carries `data-loading`, so a double Enter saves once; Tessera sends the write with a fresh `Tessera-Write-Id` and AIC's CSRF header, and AIC's write ledger answers the same write sent again without applying it. Escape or Cancel asks `@get('/app/inventory/<VIN>/row')` for the row back. A field carries `data-ignore-morph` while it is typed into, so an answer that lands meanwhile leaves what was typed; Enter, Escape and the buttons take it off before they send.

| Route | Class | Answers |
|---|---|---|
| `GET /app/inventory/{vin}/row` | `VehicleRowPage` | the row shown, or 404. |
| `GET /app/inventory/{vin}/row/edit` | `VehicleRowEditPage` | the row as a form, or 404. |
| `PUT /app/inventory/{vin}/row` | `VehicleRowPut` | the row shown with what was saved; the row as a form again, 422; 400 for props that are not this row's; or 404. |

`VehicleRowEdits` answers each as the inventory page with the list's panel holding that row alone, under the keys the list gives it (`InventoryList::KEY`, `InventoryList::RESULTS`, `InventoryTable::touched()`, framed by `VehicleRowPages::frame()`), so a Tessera request from the row finds its path on the page and AIC answers with the row's fragment alone; asked plainly, the route answers that page whole. The save is held to the row's props (`StaffSeals::rowHolds()`, through AIC's `TesseraProps`), then fills an entry from the stored vehicle with the row's `list_price` and `status` put in (`VehicleEntries::row()`) and runs `VehicleChecks::errors()` on it, the full form's own checks, before the repository's `update()`. `VehicleChecks` refuses a list price below the cost (`The list price is below the cost, $N.`), on the full form too. A refused field is marked `aria-invalid`, its message beside it, and focuses itself by `data-init`, since Tessera moves focus after a form's refusal but not after an action's.

### Edit at once

Staff tick rows and act on them together (#29). Each row's VIN cell holds a box (`name="vins[]"`, the VIN as its value) that posts with the action bar's form by its id, `vehicles-bulk`; the VIN head holds one box for the page. Above the table the results hold the bar (`BulkBar`, keyed `bulk`, anchored `inventory-bulk`, its form holding AIC's `GuardFields` from `FormTokens::guard()`, AIC #246) and the totals line (`TableTotals`, keyed `totals`, anchored `inventory-totals`): the line still says what the table shows as `#vehicles-table-summary`, then the matching vehicles counted by status (`VehicleRepository::statuses()`), then what a bulk edit did or why it was refused. The bar offers In stock, On hold, each lot location and Delete; sold is a sale's to give.

With script the selection is the region's signal `selected`, a list of VINs: the bar declares it (`data-signals__region`), each box binds to it (`data-bind:selected`) and sets itself from it after any patch, and the totals line declares it again with the page's VINs (`_page`), which the page's box ticks. A patch of the results themselves (a filter, a sort, a page) empties it. The bar's controls are disabled while nothing is ticked (`data-attr`), a count says how many are (`data-text`), and Delete opens a confirm card in the bar first. Apply sends one action, `@post('/app/inventory/bulk', {form: true, target: …})`, whose target names each ticked row's anchor and `@inventory-totals`, and nothing while the form carries `data-loading`. An applied edit's answer (200) carries a signal patch, `{"selected":[]}` scoped to `content` (`PageDocument::withSignalPatch()`, AIC #253), which Tessera merges into the region's scope once the rows and the totals line have landed, so the server that applied the batch is what empties the selection; a refusal (422) carries none and every box stays ticked.

`VehicleBulkPost` hands the post to `VehicleBulkEdits`. `VehicleEntries::bulk()` reads it into a `BulkEdit`: the choice, the ticked VINs, the page's VINs, whether a delete is confirmed, and the list it came from, kept only when it is the list's own path. In one transaction (`VehicleBatchRepository::transaction()`, the entity store's) the vehicles are read `FOR UPDATE`, in VIN order, and each is checked by `VehicleChecks::refusals()`: a status runs the full form's own `errors()` over the stored vehicle with the status put in, so a vehicle with a recorded sale is refused as the form refuses it, and sold is refused for every vehicle; a sold vehicle is not moved; a sold vehicle, or one with a recorded sale, is not deleted. When none is refused the change is one statement for all of them, and `BulkAuditRepository` queues one `notify` job per active sales manager, for the database channel alone, through AIC's `Notifier`; the queue writes through the transaction's connection, so the audit commits with the change. When any is refused nothing is written. A delete reads the vehicles' photos first and forgets their files once it has committed. AIC's write ledger answers a repeated Tessera write before the route is reached.

`VehicleBulkPages` answers. For Tessera, and for any refusal, the answer is the inventory page with the list's panel holding the bar, the totals line of the list the edit came from and the ticked rows alone, each at the path the list gives it, so AIC answers the action with those fragments: the rows as they are now, unticked; a refused row's box marked `aria-invalid` (the theme tints the row by it) with its reason under its VIN and the box still ticked, the totals line naming each refused VIN, 422. A deleted vehicle answers no row: its row's target is gone from the page, so AIC answers it with mode `remove` (AIC #247) and the row leaves the page. A ticked VIN no vehicle had answers a row in place, "No longer on the lot", with no box and no links. A plain post that succeeds answers 303 back to the list with a notice; a plain delete not yet confirmed answers the ticked rows with the bar's card open, whose Delete them posts it confirmed and whose Keep them links back to the list.

| Route | Class | Answers |
|---|---|---|
| `POST /app/inventory/bulk` | `VehicleBulkPost` | 200 with the touched rows and the totals for Tessera, 303 back to the list for a plain post; 422 with the rows when any is refused, or when nothing is ticked, nothing is chosen, or more than a page is; 200 asking first for a delete without its confirmation. |

## A vehicle's record

Each vehicle's pages are found by its VIN, not its numeric `id`: gate:23 replays the native steps on the PHP site and then on the compiled one against the same database, and a vehicle made in each pass would get a new id, so its location and every link to it would differ; the VIN the steps post is the same in both. A route's VIN is checked against the VIN alphabet (`[A-HJ-NPR-Z0-9]{17}`) before any query, and one that is malformed or on no vehicle answers 404 (`VehicleRecords`).

| Route | Controller | What it answers |
|---|---|---|
| `GET /app/inventory/{vin}` | `VehiclePage` | The vehicle's `DetailCard`: title, status badge, VIN, year, make, model, trim, body style, colour, mileage, list price and the day it came; never its cost. Edit, Delete and Back to the list, and "Record a sale" when the vehicle is not sold. Under the card, finance's payment calculator at the list price (#26), then the photos and the vehicle's sale when one is recorded (see below). |
| `GET /app/inventory/new` | `VehicleNewPage` | The blank form, in stock and on the lot from the database's today. |
| `POST /app/inventory` | `VehicleCreatePost` | 303 to the new vehicle's page, or the form again as 422. |
| `GET /app/inventory/{vin}/edit` | `VehicleEditPage` | The form filled from the vehicle. |
| `POST /app/inventory/{vin}` | `VehicleUpdatePost` | 303 to the vehicle's page (its new path when the VIN changed), 422, or 400 for the envelope. |
| `GET /app/inventory/{vin}/delete` | `VehicleDeletePage` | The `ConfirmCard`: Delete, or Keep it back to the vehicle. A sold vehicle gets a warning `Notice` and no form. |
| `POST /app/inventory/{vin}/delete` | `VehicleDeletePost` | 303 to the list; 422 for a sold vehicle; 400 for the envelope. |
| `POST /app/inventory/{vin}/photos` | `VehiclePhotoPost` | 303 to the vehicle with a notice; the vehicle's page as 422 with the reason; 403 for a salesperson. |
| `GET /app/inventory/{vin}/photos/{position}` | `VehiclePhotoStream` | The photo at that position, from 1, inline; 404 for none. |
| `POST /app/inventory/{vin}/photos/{position}/delete` | `VehiclePhotoDeletePost` | 303 to the vehicle with a notice; 400 for the envelope; 403 for a salesperson; 404 for no photo there. |

Every vehicle page is one wide `vehicle` panel in the staff pages' document, framed by `staff`'s `StaffPanels`, which `VehicleServices` builds with that id stem; the 404, 400 and sold pages are its warning page.

The form (`VehicleForm`, its grid from `VehicleFields`) is AIC's `Form` atom around the theme's `FormGrid` of `FormField`s and the status `SelectField`, then `FormActions`. No field is browser-required, so every post reaches `VehicleChecks`:

- the VIN: 17 letters and digits without I, O or Q (taken in capitals), its ISO 3779 check digit right (`Vins::checkDigit()`; the message names the digit it should be), and no other vehicle holding it;
- the year: a model year from 1981 to next year, by the database's date;
- make, model, body style and colour required, trim optional, each within its column's length;
- mileage, list price and cost: whole numbers from 0, one to seven digits;
- the status: one of the three, and sold while a sale is recorded (`VehicleSaves`; void the sale first); the day it came onto the lot: a real `YYYY-MM-DD`.

A refusal answers 422 with the error alert above the fields, each message beside its field, and every value as typed. The create's insert skips a VIN taken since the check (`EntityStore::insertIfAbsent()`), and an update that meets one on the unique key finds it taken; both answer that refusal too; the delete's condition keeps a sold row whatever the page said. A save or a delete leaves one line in the session (`StaffNotices`, the `staff` module's, which customers share) for the page it redirects to, which shows it as a success `Notice` and clears it.

The edit and delete forms carry AIC's signed envelope sealing the vehicle's path (`StaffSeals`, over `EnvelopeCodec`, from `staff` too). A post whose envelope is missing, altered or sealed for another vehicle's path answers 400 and changes nothing, so a form issued for one vehicle cannot change or delete another. The CSRF token and honeypot are the `Form` atom's.

## Price history and the panels

`CreateVehiclePricesTable` makes `vehicle_prices` (#31): an identity `id`, `vehicle_id` (cascading with the vehicle, indexed), `from_price` and `to_price` (whole dollars) and `changed_on` (the database's today), with `created_at`. `VehicleTable::prices()` is its entity type, beside the vehicles' own. `VehicleRecordRepository::update()` runs in the entity store's transaction: `updateLocked()` locks the vehicle's row, writes every value, and when the list price is another inserts the change, so the full form's save and the row's save both record it and a save that fails records nothing. A new vehicle, a save that keeps its price, the seed and a bulk edit record none. `VehiclePriceRepository`, exported, reads a vehicle's newest changes by its VIN, oldest first, and their version.

After its sale the vehicle's page places the panels the `VehiclePanel` plugins give, the plugin type inventory exports for them as it exports `VehicleSales` for the sale. The `panels` module registers three: the price history, the vehicles like it and its leads and holds; its README says how each loads. `VehicleCards` asks each plugin for a skeleton when the request is a Tessera visit, and for the panel inline otherwise, so a page asked plainly, as with JavaScript off, shows them with no second request. `VehicleRepository` gives the panels the vehicle by its VIN (`find()`) and the vehicles like it (`similar()`, `similarVersion()`): not sold, of its make and body style, nearest its list price.

In the list, a row's VIN link carries `data-prefetch="hover"` (`TableCell::$prefetch`, #43): resting the pointer on it for Tessera's 60 ms, or focusing it from the keyboard (Tessera 0.4.4), sends the visit early, and the click or Enter that follows paints from that answer, one request, with the panels as skeletons. A press alone prefetches as it always did. Tessera takes a hover's answer only when it is not `no-store`, so the vehicle page opts in with `PageDocument::prefetchable()` (AIC #254) and its 200 answers `private, no-cache`: the page shows no cost, and what changes on it, the panels, comes from their own routes, which stay `no-store`, as do its 404 and a refused upload's 422. Since Tessera 0.4.4 a press drops a pending hover timer, so a quick click sends no second prefetch. The price and status cells keep `data-prefetch="off"`. The gallery's photo strip carries `data-permanent` and the id `vehicle-photos-<VIN>-<count>-<tag>`, the tag from the newest photo's bytes, so Tessera keeps it, scrolled where it was, across a redraw that brings the same photos, and an upload or another vehicle gets a new one.

## Photos

A vehicle's photos (#16) are the `photos` module's: its table, its files in AIC's public files (#23) and its gallery. Inventory requires it and keeps the routes, since a refused upload answers the whole vehicle page, which only inventory builds; `photos` knows a vehicle by its numeric id alone, which `VehicleRecords::vehicleId()` finds by the route's VIN. `VehiclePhotoForms`, in `Form/`, holds the three routes' flows:

- an upload from a sales manager or an admin goes to `VehiclePhotos::add()`; its refusal (no file, a file AIC's `UploadCheck` refuses by its content or its size, a thirteenth photo) answers `VehicleCards::page()` with the reason and 422, and Tessera puts it in place; a kept photo answers 303 to the vehicle with "Added a photo of the {title}.";
- a delete names the photo by its position, and its form seals that photo's id (`VehiclePhoto::sealed()`), so a form from a page that is out of date answers 400 instead of deleting the photo now at that position;
- a kept upload and a done delete each queue the vehicle's photo bundle through photos' `PhotoBundles::queue()` (#36), so the `photo-bundle` job rewrites its ZIP, and its brochure through `Brochures::queue()` (#44); a refused one queues nothing;
- the Stream answers `VehiclePhotos::download()`: AIC's `FileDownload` of the photo's file in the public files, with the request, which sends the ETag, `Last-Modified` and `Cache-Control: private, no-cache` and answers ranges (206, 416) and conditions (304, 412). The gallery itself shows each photo from its `/files/` URL.

`VehicleServices` builds `VehiclePhotoForms` with the photos' service from the public files, so the photo routes' generated part is one short method.

A salesperson's upload or delete answers 403 (AIC #197) and changes nothing; their page shows the photos with no form. The vehicle's page shows the gallery under its card, keyed `photos`, with the ZIP's link once its bundle is written; `VehicleServices` takes photos' `PhotoBundles` and hands it to the gallery. The ZIP's own route, `/app/inventory/{vin}/photos.zip`, is the `downloads` module's (#36). Deleting a vehicle deletes its photo rows by their foreign key, and `VehicleDeletes` then hands `VehiclePhotos::forget()` the photos it read before the delete, which removes each file no other photo holds. A deleted vehicle's photo bundle stays in the private files, out of reach: its route answers 404 once the vehicle is gone.

## The brochure

A car's one-page brochure (#44) is built and served by storefront from its view of the car; inventory only says when the vehicle changed. A vehicle created or saved from its form (`VehicleSaves::saved()`, both 303), a row saved in place (`VehicleRowEdits::save()`, 200), and a photo added or deleted (`VehiclePhotoForms`) queue storefront's `car-brochure` job through the `brochures` module's `Brochures::queue()`, with the vehicle's id; a refused form queues nothing. Inventory requires `brochures`, a module that requires none, since storefront, which declares the job, requires inventory. `VehicleServices` takes `Brochures` and hands it to `VehicleSaves`; the wiring hands it to the other two. A bulk edit, a hold, a sale or a delete queues nothing: they change whether the car is for sale, not what its brochure shows, and storefront serves a brochure only for a car in stock. `ListedVehicleRepository::listing()` reads one car for sale by its id, for the job.

## Sales

The `sales` module requires inventory, so inventory cannot require it back. It exports a plugin type instead, `VehicleSales` (with its value `VehicleSale`), and `sales` registers its implementation. `VehicleServices` takes every plugin with `#[Tagged(VehicleSales::class)]` and hands them to `SoldVehicles`, which asks them for a vehicle's sale and for the path of the form that records one; the generated provider builds a plugin with no arguments, so the entity store comes with each call. With a sale, the vehicle's page shows a "Sale" table (`vehicle-sale`: the day linked to the sale, the customer linked to theirs, the salesperson and the price), and the edit form refuses any status but sold. Without one, a vehicle that is not sold gets "Record a sale" (`vehicle-sell`), which opens `/app/sales/new?vehicle={VIN}`. Without the `sales` module, the page shows neither.

`VehicleStatusRepository`, exported, is how `sales` changes a vehicle: it locks a vehicle's row while a sale is recorded and sets its status (sold, or in stock when a sale is voided), on the caller's transaction. `holds` (#20) goes through it too: `lockedStatus()` locks a vehicle's row and gives its status before a hold is placed or released, and `mark()` sets it on hold or back in stock. A delete that meets a sale's foreign key, because a sale landed after an edit's check, answers the delete page as 422 (`VehicleDeletes`). Inventory also exports what the sales seed builds its sold vehicles with: `Vehicle`, `VehiclePrice`, `VehicleStatus`, `Vins`, `VehicleRepository` and `SeedVehicles`; and `VehicleTable` and `TodayRepository`.

## Seed

`bin/aic inventory:seed` takes no arguments (exit 2 with its usage otherwise) and saves 60 invented vehicles, five each of twelve makes (`SeedVehicles`). The same 60 come out every run, so a rerun updates the same rows by VIN. Each VIN (`Vins`) starts with `0LT`, a world manufacturer identifier no region is assigned, and carries the model-year code and a valid ISO 3779 check digit, so it is well formed and can belong to no real vehicle.

Run `bin/aic migrate` first. From the host, point both at DDEV's published Postgres port (`PGPORT`, from `ddev describe`), or run them with `ddev exec`.

## Checks

`config/native-site.json` asks for the list signed out (303), signs in again, then asks for it plain, filtered, sorted, at page 2 and with malformed parameters. Then it walks a vehicle's record with the fictional VIN `0LTGATE19SR999001`: the new form, a create refused on every field, on its check digit and on a taken VIN (422 each) and with no token (403), the create (303), its page and edit form, an update with an altered envelope (400), a refused update (422), an update to sold, the sold vehicle's delete page and its refused delete (422), back in stock, the delete page and the delete (303), the list with its notice, and 404 for the deleted vehicle's page and edit form and for a malformed VIN. ## The payment calculator

## The cars a comparison reads

The storefront's comparison (#33) names cars by their public slugs, which end in a key: the first 6 hex digits of the SHA-256 of the VIN. `CreateVehicleListingsView` makes the view `vehicle_listings`, every vehicle in stock with the columns a `ListedVehicle` is read from and `listing_key`, the key worked out in SQL (`substr(encode(sha256(convert_to(vin, 'UTF8')), 'hex'), 1, 6)`). `VehicleTable::listings()` is its entity type. Every read of `ListedVehicleRepository` goes through it and takes each car's key from its row, so PHP works out no key. `compared()` reads the cars with the keys it is given in one statement (`whereIn('listing_key', …)`), by VIN, as `ListedVehicle`s, so the VIN and the cost stay here. A key may be shared by two cars, so the compare module keeps only the cars whose whole slug is the one asked for.
